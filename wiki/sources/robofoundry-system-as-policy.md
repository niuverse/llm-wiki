# RoboFoundry：把系统本身作为可改进策略

## 概览与问题

RoboFoundry 的对象是固定基础模型之外的执行系统：上下文构造、记忆选择、提示、技能接口与执行代码。论文把同一个冻结模型在不同系统中的行为差异称为 system-as-policy，并通过执行记录驱动系统修改。本页完整阅读 v1 正文、参考文献、附录案例与分任务表；未运行系统。证据来自[原文](https://arxiv.org/html/2609.32862v1)，不能把系统提升解释为模型权重学习。

它与 [[gap-graph-as-policy|GaP]] 的连接是将可执行外部结构视作策略；区别在于 GaP 重点约束技能图，RoboFoundry 还修改决定模型“看见什么、记住什么、调用什么”的系统。与 [[racap-evolvable-robot-learning|RACaP]] 比较时必须先区分冻结评测和在线演化。

## 机制：任务修复怎样变成共享规则

固定模型记为 $M$，系统 $H$ 分成任务专属部分 $H_t$ 与跨任务共享部分 $H_g$。执行阶段是 $H(M)$ 根据观测和历史生成动作；外层将轨迹、反馈、失败和改动关系写入演化账本，再提出候选修改。论文 §2 将可修改面分成两组：

- 上下文侧决定 SAVE、RETRIEVE、UTILIZE：保存哪些事件、从外部存储取回哪些视觉或文本信息、如何组成当前输入。记忆库和当前上下文是两个对象。
- 技能侧把手工验证的原子操作组合成技能，并用恢复树处理失败；语义绑定解决“任务指的是谁”，机器人绑定解决“怎样在此本体执行”。原子控制能力不是由零生成。

一个具体案例是“先移动黄油，再移动奶酪”。旧格式器始终传原始总任务；修改后读取已完成阶段，只把下一未完成阶段、总目标与“不要撤销已完成步骤”放入当前上下文。另一个案例是将对象中心目标换成 TCP 目标：$p_{TCP}^{target}=p_{object}^{target}+(p_{TCP}^{current}-p_{object}^{current})$，把持物偏移藏进复用技能，而不是让每次生成的代码重估。后者依赖抓持关系在搬运中近似保持；这些是附录 A 的实例，不是任意抓取都成立的保证。

推广有两道不同的检查。任务修复由新的执行检验；共享规则的保留检查则取其他任务中同能力类别的成功记录，重放修复前信息，让候选共享规则提出任务修复，再由系统中的验证模型比较该修复与历史成功修复。能力增益非负才推广。**这里的 held-out 检查包含轨迹重放和模型评分，不能等同于所有保留任务都重新完成物理执行，也不是独立于改进器的外部评测。** 原文 §2 的验证定义应与真实执行增益分开看。

## 执行与持久化接口

一次循环依次为观测／任务 → 选择上下文与技能 → 执行 → 记录动作及结果 → 诊断能力缺口 → 修改任务系统 → 执行检查 → 提取通用规则 → 保留检查 → 提交共享系统。附录区分执行目录、演化账本和单次尝试代码：例如 EmbodiedBench 的提示与 planner 文件承载长期规则，`.robofoundry/` 保存版本和证据，episode 记录保存实际输入输出。这里是论文附录描述，未核查独立代码仓库。

LIBERO 案例还区分跨任务技能更新和单次尝试的恢复。普通搬运被归入 `pick_and_place_sim_object(...)`；推开障碍再重抓可能只属于当前尝试。保存一段执行日志不自动意味着系统已经把其中的恢复策略推广成通用技能。

真实实验共享冻结的 GPT-5.5 和同一微调后的 $\pi_{0.5}$ 执行底座，因此比较针对外部系统；它不说明不需要机器人训练数据。G1 导航和六步化学操作案例主要展示系统组成，不应与定量表合成统一成功率。更大上下文也不是单调增益：正文与附录的 16K 实验仍需按模型和预算分别看。

## 局限与我们的解释

来源支持“执行系统可以成为学习对象”，尤其展示了记忆格式、检索、接口语义等可持久化改变。它还说明 [[RobotHarness|机器人 Harness]] 不止是一个提示词或工具目录。与此同时，共享规则的推广依赖模型验证，可能保留看似合理但执行无益的修改；在线累计分数混合了初始能力、适配速度与后期能力。

按照 [[PhysicalRecursiveSelfImprovement|Physical RSI]] 的严格分析口径，本工作提供系统级自改进证据，但仍需单独比较“演化后的改进程序”和固定改进程序在新任务、相同执行预算下的学习效率，才能判断改进能力本身是否提高。这个要求是我们的评测建议，不是论文已完成的实验。
